## Explicit loading

Use the existing service-local Python 3.12 `.venv` and requirements.txt. New pins
are `PyJWT[crypto]==2.15.1` and `cryptography==50.0.2`. Installation, pip consistency,
in-memory RS256 signing/verification and Fernet compatibility were checked.
Versions were read from the package registry, not guessed. HTTPX remains the
existing provider transport; no new identity microservice is introduced.

```python
from statistics_agent.core.auth import load_auth_settings
from statistics_agent.core.auth_secrets import load_auth_secrets

settings = load_auth_settings(env_file=".env.auth")  # Explicit local configuration.
secrets = load_auth_secrets(settings)  # Explicit protected-file reads, when needed.
```

Do not print the secrets object or its values. Configuration loading alone reads
no secret files and contacts no provider/database. No module automatically loads
dotenv or credentials at import. Process variables override explicitly selected
dotenv values; relative paths use the calling directory. Deployment injects
settings/secret-file mounts and omits dotenv. Missing/invalid inputs produce fixed
ConfigurationError diagnostics without raw source exceptions or input values.

For programmatic validation, `.env.auth.example` may be copied to ignored
`.env.auth` and loaded explicitly as above. For the current Uvicorn startup, add
these references to the existing ignored `.env` or process environment; the factory
does not implicitly load `.env.auth`. Keep DATABASE_URL and `.env.postgres` intact.
Both new secret paths are required references. Configuration can be validated
before those files exist; explicit secret loading rejects missing/invalid files.
No real secret file or key was generated by this implementation.

## Trusted provider and browser policy

Issuer is an exact canonical `/realms/<name>` URL. Discovery endpoints must match
the issuer's fixed Keycloak OIDC paths, including JWKS and introspection. The
metadata validator performs no request. It requires RS256 support; the trusted
algorithm allowlist is exactly RS256 and never follows a token's alg header.
The pinned Keycloak 26.8.1 source declares RS256 as its default; no live provider
configuration was queried here. Actual metadata/token verification comes in 3.3.

URLs reject credentials, queries/fragments, ambiguous host spelling, encoded or
dot paths and noncanonical authorities. Local HTTP is allowed only in explicit
development/test on localhost, 127.0.0.1 or ::1. Staging/production require HTTPS.
Public origin has no path/trailing slash; callback must be that origin plus
`/auth/callback`. No arbitrary return URL or external callback is accepted.

Cookie security follows the public scheme. Explicit contradictory values are
rejected. SameSite policy is lax only. Planned session name is
`__Host-agent-session` in staging/production and `agent-session-dev` in local/test.
The future cookie writer must also enforce HttpOnly, Path=/ and no Domain; no
cookies are written in 3.1. There is no configuration flag to bypass permission
checks. HTTP phase limits must fit the total deadline; session idle/absolute limits
cannot exceed the existing 30-minute/8-hour provider contract. Login attempts
are bounded to five minutes. These limits are configuration, not active sessions.

## Secret-file formats

`OIDC_CLIENT_SECRET_FILE`: the actual Keycloak-generated client secret, one line,
16–4096 ASCII credential characters; an optional final LF/CRLF is allowed.
Whitespace, common placeholders and oversize input are rejected. Retrieve the
value through the protected Keycloak client Credentials page; never place it in
browser code, logs, source control or a command argument.

`AUTH_TOKEN_ENCRYPTION_KEYS_FILE`: UTF-8 JSON, at most 64 KiB:

```json
{
  "active_key_id": "local-1",
  "keys": {
    "local-1": "REPLACE_WITH_A_REAL_FERNET_KEY"
  }
}
```

The placeholder is deliberately invalid. Provision actual keys using
`cryptography.fernet.Fernet.generate_key()` through a protected channel before
starting the current application. Never regenerate them on routine startup.
Each value must be canonical URL-safe base64 for 32 bytes. One to five unique
key values are allowed, with a present active ID; duplicate JSON fields, duplicate
material, malformed keys and unknown fields fail safely. Keys are identified by
ID, not object order. Active/read keys provide the format for later rotation;
3.1 does not rotate keys or encrypt stored tokens. Lost keys cannot be recovered
from database ciphertext.

Use ignored `secrets/` or deployment secret mounts, with restricted filesystem
permissions/Windows ACLs. Filesystem access control is an operator responsibility,
not a claimed guarantee of this parser. Both secret paths and key material are
excluded from model repr/serialization; explicit value extraction remains
sensitive. Secrets must remain separate from PostgreSQL backups and client code.

## Authorization-policy revision — 27 October 2026

The plan now uses local JWT authorization with trusted cached public keys and
five-minute access tokens. No per-request introspection. Existing 3.1 types,
RS256 policy, secret references and provider endpoint metadata remain usable; the
introspection endpoint is retained for compatibility/diagnostics, not normal API
requests. Step 3.3 now implements the cache and initial login-token validation. Step 3.4 now wires protected requests and demonstrates bounded token-expiry
behavior, role replacement and trusted-key outage continuity. Step 3.5 now implements provider renewal and logout; broader handoff remains 3.6. Cache trust is bounded to one hour; unknown/expired trust and
required renewal still need identity connectivity. Local logout remains immediate.
Browser cookies, encrypted server tokens, refresh coordination and CSRF remain.
No runtime code, dependency or test changed in this documentation revision.
