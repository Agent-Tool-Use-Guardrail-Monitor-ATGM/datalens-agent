# Authentication storage — step 3.2

Step 3.2 introduced internal PostgreSQL repositories for browser sessions and
pending logins. Step 3.3 now connects them to login/callback and startup; see
[browser login](browser-login.md). Step 3.4 adds [ongoing request authorization](request-authorization.md); automatic
refresh and logout remain later steps. Storing a credential or constructing a principal
does not verify it. The verification evidence below records the original 3.2 step.

## Tables and migration

`0002_auth_storage` follows `0001_agent_baseline` and creates only agent-owned
`auth_login_attempts` and `auth_sessions`. Use the existing explicit migration
command when updating the development database:

```powershell
.\.venv\Scripts\python.exe -m statistics_agent.persistence.migrate upgrade --env-file .env
.\.venv\Scripts\python.exe -m statistics_agent.persistence.migrate check --env-file .env
```

PostgreSQL must already be running. This step tested only disposable
`agent_test_db`; it did not migrate persistent development data. Readiness rejects
an older schema until the explicit upgrade succeeds. Startup does not migrate it.

Downgrading this migration deletes all local sessions and pending logins. Users
must sign in again. It neither modifies Keycloak nor deletes identity accounts.
The existing CLI permits destructive downgrade only against the designated test
database; production rollback requires a separate, reviewed migration procedure.

## Login attempts

`AuthStore.start_login` creates independent 256-bit random state, browser binding,
nonce and PKCE verifier. State and browser binding are stored as SHA-256 hashes;
nonce and verifier are encrypted. The initiating browser must later present both
state and binding. Their cookie/redirect handling belongs to step 3.3.

An attempt expires after at most 300 seconds, with shorter configured limits
supported. Only one unconsumed attempt per binding is permitted. A conflicting
start raises `PendingLoginError`; it never replaces a live attempt. An expired
attempt is retired before a replacement can be inserted. Consumed bindings may
start another attempt. Separate browsers may have independent attempts.

`consume_login` atomically marks a matching, unexpired attempt consumed and commits
before decrypting or returning credentials. Concurrent callbacks have one winner.
Wrong state or browser binding does not consume the legitimate attempt. A later
decryption or token-exchange failure cannot reactivate a consumed attempt. The
only stored return target is `/`; no client-selected redirect is accepted.

## Sessions and encryption

The browser credential is another independent 256-bit random value. SQL stores
only its hash. The internal session UUID is a reference, not a browser credential.
Sessions retain exact issuer/subject ownership, creation/activity timestamps,
idle and absolute deadlines, local revocation and a refresh version. They store
no positive roles or verified-email authorization snapshot.

Access, refresh and optional ID tokens use Fernet authenticated encryption, with
keys loaded explicitly through the existing external keyring. Each encrypted
payload includes its version, row UUID, issuer, subject and secret kind. Decryption
compares these with trusted row context; moving ciphertext to another row, owner,
issuer or token column fails. Attempt nonce/PKCE envelopes use the same binding
with an empty subject before login. Neither raw tokens nor random browser
credentials enter SQL, object representations or application logs.

Envelopes carry a key identifier. Writes use the active key; reads may use retained
older keys. Keep previous keys until their records expire or are deliberately
re-encrypted. Restart with the same keyring retains readable state. A missing,
wrong or removed key raises a fixed `SecretEnvelopeError`; storage is never reset
or accepted as plaintext. SQL backups therefore also require a separately secured
key backup. No real key or client secret was generated by this step.

Secrets are limited to 32 KiB each. Session expiry depends on explicit DB
deadlines, not Fernet timestamps. Reads neither renew credentials nor extend idle
time. Only a later successful authorization may call `touch_session`, which never
extends the absolute deadline or revives an expired/revoked session.

`replace_credentials` provides atomic version-checked persistence: concurrent
updates at the same version have one winner. It preserves the browser credential
and cannot update a revoked/expired session. **This is not refresh coordination**:
step 3.5 must prevent multiple replicas from exchanging the same refresh token
before contacting Keycloak and handle uncertain exchange outcomes.

All repository operations own short transactions and return after commit. They
perform no remote calls. Optional `now` arguments accept only trusted server time
for deterministic tests, never client-supplied timestamps.

## Cleanup and verification

`AuthStore.cleanup(limit=100)` explicitly deletes at most the requested number of
expired/consumed login attempts and expired/revoked sessions across both tables.
The limit must be 1–1000. It skips rows locked by other transactions and does not
delete live records. No scheduler or extra service is introduced; arrange periodic
operator/job invocation when browser access is integrated.
